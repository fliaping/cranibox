# Cranibox 与 Orca、OpenClaw：价值定位与开源发布策略

初次调研日期：2026-10-14；产品优先级更新：2026-10-16。本文是产品判断与验证计划，不代表其中的下一代节点能力已经实现，也不保证传播结果。竞争项目以官方仓库与文档为依据；本项目同时检查当前工作区源码、构建流程和设计草案。

维护者已明确先让自己的多设备工作好用。当前主线是统一项目/会话视图、对等连接、跨设备 Agent 沟通，以及项目与会话接续，详见[新的工作空间设计](distributed-agent-workspace-design.md)。2026-10-16 复核还确认 Orca 已有 federated workers，不能把跨设备编排当作空白市场。下面 2026-10-14 的竞争快照仍用于比较，传播建议在日常使用闭环之后再执行。

核对的公开 main 提交：

- Cranibox：`547165d50b468ed13a0313140331888398bfa1b7`，2026-10-13。
- Orca：`75513668fb20442f23a9ab530adb3cf628bce747`，2026-10-14。
- OpenClaw：`70409b38bb91d0520374579d76fb41550b1872bf`，2026-10-14。

以上是源码和文档快照，不等于三者最新稳定安装包已交付所有描述的功能。本文没有对竞争项目做完整实机测评。

## 1. 判断

Cranibox 当前要先做成自己愿意每天使用的多设备项目与 Agent 工作空间：所有设备接入后，从同一套界面查看项目、继续会话、让不同设备的 Agent 交互，并在需要时迁移工作。设备能力接入是这一工作流程的基础。

Orca 的主要使用入口是开发工作台；OpenClaw 的主要使用入口是助手、会话和消息渠道。Cranibox 可以把它们当作接入方：用户不必换掉自己的 Agent，也不必把其他机器上的软件、浏览器登录态和工作环境搬到新的中心。

这只是值得验证的定位。Orca 和 OpenClaw 都已经跨越了单机 Agent 的边界。仅提供远程命令、MCP、浏览器、桌面、多个 Agent 或开源，并不足以证明用户有理由再安装 Cranibox。

建议面向用户的介绍：

> 把自己的设备连起来，让项目和 Agent 工作可以随时查看、跨机协作和接续。

英文可以使用：Connect your devices. Keep your projects and agents working together.

“对等节点”“EasyTier”“Tailscale”“Rust”放在解释实现方式的位置。首页首先回答能完成什么任务、第一次成功需要几步。

## 2. 能力重叠与产品入口

| 维度 | Orca | OpenClaw | Cranibox 当前与目标 |
| --- | --- | --- | --- |
| 主要入口 | 多个 CLI Agent、worktree、终端、审阅与浏览器组成的开发工作台 [S1] | 自托管助手，Gateway 连接会话、工具、消息渠道及设备 [S3][S4] | 当前是容器 Workspace 与节点控制中心；建议突出已有 Agent 的跨设备能力接入 |
| 多种 Agent | 已支持多种 CLI Agent，不能用“我们支持多个 Agent”来区分 [S1] | 模型与 Agent harness 可替换，节点也有外部 Agent 会话目录 [S3][S5] | 现有 CLI/MCP 接入；下一步证明不同 Agent 能复用同一设备能力和权限 |
| 远程执行 | SSH worktree、远程后端及独立运行的服务；手机可继续监控和操作 [S1][S2] | 配对节点暴露本机执行等能力，官方架构以 Gateway 连接客户端和节点 [S4][S5] | 已有 WebSocket 命令网关、原生 PTY 与任务；仍经过 Workspace |
| 浏览器与桌面 | 浏览器操作和 Computer Use 已存在，具体桌面能力有平台限制 [S1][S8] | 已有节点浏览器代理、Computer Use 与桌面面板；Windows/Linux 的 CUA 路径标为实验性 [S6][S7] | 容器已有托管浏览器和 Selkies/桌面桥接；原生节点的完整浏览器、VNC 与 Computer Use 尚未交付 |
| 组网与运行边界 | 官方重点是工作台、远程后端和移动配对，不能从这些文档推断不存在其他互联能力 [S1][S2] | 官方节点是 Gateway 的外围设备；这与对等能力节点设计不同 [S4][S5] | 下一代拟让 Docker、桌面、无界面节点身份一致，能力执行与授权由目标节点持有 |
| 开源 | MIT [S1] | MIT [S3] | 根目录尚未发现项目 LICENSE；需要明确项目和分发组件的许可 |

OpenClaw 还支持节点发布 MCP 工具与 Skills。它提供的外部 MCP 服务也不能被忽略；具体工具范围需要核对，不能把“可以接其他 Agent”说成 Cranibox 独有的能力 [S5][S9]。

从产品表达看，Orca 让开发者直接理解“同时管理多个编码任务”，OpenClaw 让用户理解“从熟悉的入口使用自己的助手”。这是对其官方介绍的分析，不是对其增长原因的统计证明。Cranibox 也需要同样直接的任务表达。

## 3. 最值得验证的三个价值点

### 3.1 能力留在原来的设备上

用户的 Windows 软件、Mac 工作环境、服务器计算资源和已登录浏览器不必迁入一个新的 Agent 平台。Agent 通过明确授权使用对应设备上的能力。

最适合的首批用户，是已经有两台以上设备、已经在用 Agent 的开发者和自托管用户。他们有实际跨设备任务，也有能力描述安装与连接中的问题。先不把家庭普通用户、企业多人权限和大型设备管理同时作为目标市场。

这里的优势要由体验证明：一个节点安装包、简单配对、一次接入 Agent、清楚的目标选择。OpenClaw 节点和 Orca 远程后端已经解决了一部分相同问题，所以“有这个功能”不够；必须让这类用户更容易完成任务。

数据在原机执行也不等于所有信息永不外发。截图、任务结果和模型上下文仍按用户配置发送到 Agent 或模型提供方；对外介绍不能把自托管等同于零数据出境。

### 3.2 没有必须在线的应用中心

拟议架构让设备之间直接验证身份与目标授权；Workspace 的 Web、引导与中继是可选角色。已有可信节点在路径可达时，可以在某个 Workspace 离线后继续调用对方，不必连接固定主节点。统一视图也不要求选主。

这是当前比较中最值得做原型的技术差异，但尚未实现。演示必须真的停止 Workspace，再从一个节点调用另一个节点。仅断开浏览器、切换 Tailscale 地址或让本机 Shell 继续运行，都不能证明应用层已经无中心。

成立条件包括有效的缓存信任信息、目标策略和可达网络路径。唯一可用中继离线时连接会失效；休眠设备不能执行；Tailscale 本身仍使用自己的协调体系。不要承诺任意网络条件下永远连通。

用户未必为了“去中心化”安装软件。需要把它翻译成可感知的收益：服务器维护不影响两台电脑互用；换控制台入口能找到同一目标任务；设备之间不必绕经一个固定应用网关。

### 3.3 Agent 与用户一起使用真实会话

同一目标上的终端、浏览器和桌面允许人查看、暂停、接管，再交回 Agent。控制权、权限拒绝和当前目标始终可见。移动端主要承担查看、确认和短时接管，复杂编辑仍以大屏为主。

OpenClaw 已在其云环境桌面中描述相同会话、人工接管和停止 Agent 输入的行为；其文档明确这套控制权仲裁不适用于普通 Gateway 或配对节点桌面。Orca 也有移动操作与桌面控制。因此人工接管本身不是独占功能 [S2][S7]。机会在于把跨 Agent、跨系统原生节点的控制与交接做完整，而不是再做一个 VNC 页面。

需要实际证明休眠唤醒、网络切换、权限撤销和断线重附着。现有原生 PTY 只有在节点进程和 Shell 仍存活时才能恢复附着；电脑重启不恢复旧 Shell。不能用网络重连演示代替进程恢复承诺。

## 4. 不能独立作为主卖点的东西

| 说法 | 为什么不足 | 应该提供的证据 |
| --- | --- | --- |
| Rust，所以很轻 | 实现语言不能代表包含浏览器、桌面和 sidecar 后的总资源成本 | 相同机器、相同任务下的空闲内存、CPU、安装体积；分别报告节点核心和完整桌面环境 |
| 开源、自托管 | 两个比较项目已是 MIT 开源 | 明确许可证、可构建源码、可验证发布和用户可控的退出方式 |
| 支持远程命令或多个 Agent | 已有大量能力重叠 | 首次接入时间、目标识别准确性、跨 Agent 复用和恢复体验 |
| 内置 EasyTier/Tailscale/VNC | 集成已有工具能够减少配置，但本身易被复现 | 比手工拼接 VPN、SSH、桌面和 MCP 更少的步骤、更清楚的授权和排错 |
| 功能最全 | 容易把项目变成另一个难配置的平台 | 一段可重复完成的真实跨设备任务 |

较难复制的积累，是平台兼容性、能力适配器、可靠恢复、清楚的权限和健康的贡献者群体。它们仍需时间建立，不能把未来路线图称为已形成的壁垒。

## 5. 当前推广前的具体缺口

1. **定位与第一屏。** README 目前强调“自托管、可信任的 Agent 大脑”和完整容器环境。若采用新的设备能力定位，轻量节点应当有独立安装入口；完整 Docker Workspace 可以作为持续在线的可选节点和 Web 入口。不要让所有新用户先搭建完整容器桌面。
2. **公开下载。** 节点 CI 已有三个系统的产物，但当前入口是 Actions Artifacts。GitHub 官方要求登录并具备读取权限，产物还存在保留期限 [S11]。应发布带固定版本、校验和和平台说明的 Releases 安装包。现有容器镜像发布不等于节点安装包已这样交付。
3. **签名与平台实测。** 现有文档明确没有发布者签名或 macOS 公证。需要把正常安装、系统授权、托盘、自启动、升级、卸载和休眠恢复作为发布验收。CI 构建和模拟 IPC 测试不能替代这些体验。
4. **明确开源许可。** 根目录未发现 LICENSE。GitHub 文档说明公开仓库与开源许可不同 [S10]。维护者应确定项目许可，并核对安装包内第三方组件的分发要求和 notices；本文不替维护者选择许可证。
5. **承诺与现状分开。** 当前跨节点命令依赖 Workspace，同组设备互相信任；EasyTier 对等连接、目标节点细分授权、原生节点 VNC 和共享完整控制台仍是设计。宣传和下载页必须对应实际版本。

源码依据：[节点客户端说明](node-desktop-and-device-mesh.md)、[下一代设计](decentralized-node-network-design.md)、[构建流程](../.github/workflows/rust-runtime.yml)、[当前 README](../README.md)。

## 6. 传播应该围绕一个完整任务

建议第一段公开视频展示：

> Mac 上正在使用的 Agent 调用 Windows 电脑上的专属软件完成一个任务；用户从手机看到同一个桌面并接管确认，随后交回 Agent，结果返回原来的会话。

这是需要实现和实测的演示目标。当前版本可先展示 Mac/服务器上的 Agent 经 MCP 调用 Windows 的 PowerShell、查询输出，以及浏览器终端重附着。没有实现的原生桌面和对等调用不能通过剪辑暗示已经可用。

视频控制在约 60–90 秒，先展示结果，再展示首次安装和配对。使用可公开的测试数据，让观众能复现同一任务。对等原型可另外提供“关掉 Workspace，已授权且可达的两个节点仍能调用”的连续录像，作为架构证据。

不要在第一段视频同时解释 VPN、选主、NodeID、服务注册、十个页面和所有 Agent。它们在文档里回答工程问题，不承担吸引首次使用的任务。

## 7. 建议执行顺序

### 阶段 A：先完成自己的日常使用闭环

先按[多设备工作空间交付顺序](distributed-agent-workspace-design.md#8-按日常可用的纵向流程交付)完成共享项目视图、对等调用、跨机消息与委托，以及手动项目/会话接续。以维护者自己的真实设备和常用 Agent 验收，记录每天找回会话、跨机执行和迁移遇到的阻塞。

对等原型必须验证关闭原 Workspace 后，授权且路径可达的节点仍能新建调用；统一视图必须能从两个入口找到同一会话；迁移必须保留未提交修改并避免源/目标同时执行。这些都是要实现和实测的目标。

自己持续使用后，再邀请其他有多设备工作流的用户试用，了解现有 Orca、OpenClaw、SSH 或文件同步工具还留下哪些问题。外部验证用于修正体验与产品边界，不作为开始解决个人工作流的前提。

### 阶段 B：形成可以推荐给朋友的版本

交付稳定节点 Releases、正常的系统安装体验、配对向导、明确权限、Agent 接入示例、诊断与卸载。优先覆盖一个有实际差异的跨系统任务，再扩充能力目录。

建议先正式维护两个经过实机验收的 Agent 接入路径，其余标注兼容性范围。为 Orca/OpenClaw 提供使用 Cranibox 能力的适配方案，让其用户增加设备，而不要求迁移会话、记忆和工具配置。官方是否提供合适的扩展点，需要在实现时按固定版本核对。

公开文档包含 LICENSE、第三方 notices、贡献入口、问题模板和安全问题报告渠道。小任务可按平台后端、诊断、安装与文档拆分，给贡献者可复现的环境和明确验收标准。

### 阶段 C：集中发布并按使用反馈迭代

README 首屏只放一句定位、短演示、下载和最短入门；中文和英文保持同等完整。说明已交付能力、实验性范围和下一步，不把设计草案放进稳定功能列表。

选择已有实际用户的 Agent、自托管和开发者社区发布复现任务、安装说明和技术设计；Show HN、GitHub、相关社区及中文视频渠道是可选的传播入口。遵循各社区规则，先得到用户反馈，再集中发布更成熟的版本。本文仅建议传播方式，没有向外发送或发布内容。

重点展示用户真实完成了哪些任务、安装卡在哪里、下一版修好了什么。转发奖励和 Star 数不能替代使用证据。

## 8. 观察什么，如何决定继续投入

下面是试点阶段建议采用的目标与指标，不是行业基准：

| 指标 | 定义和用途 |
| --- | --- |
| 首次成功时间 | 从下载开始，到原有 Agent 调用第二台设备；以 5 分钟内作为改善目标 |
| 安装完成率 | 分系统记录成功数、尝试数与失败原因，避免只统计已经成功的用户 |
| 首次任务成功率 | 使用可复现任务；把网络、权限、驱动、Agent 选错目标分别计数 |
| 第二次真实任务 | 首次成功后，用户是否主动再次使用，而不只是观看演示 |
| 七天留存 | 固定入组用户中，一周后仍完成跨设备任务的人数 |
| 持续在线与恢复 | 在真实休眠、网络切换和入口故障中，记录恢复时间、失败及任务重放 |
| 安全与可控性 | 未授权请求被拒绝，撤销及时生效，人工接管不继续注入，重试不重复执行副作用 |
| 推荐理由 | 用户能否说清楚为何比现有工具更适合自己的任务 |

若用户只在演示当天使用，应先改场景和接入成本。若经常使用但不推荐，优先改稳定性和说明。如果他们愿意把第二台、第三台设备接入，并让不同 Agent 复用，才值得继续扩展网络和能力服务。

“爆火”不可保证；最有机会传播的形态，是一个用户能立即理解、短时间复现、用过后还会再次使用的跨设备任务。
